System prompts are often shared (identical) across all users of an app; last user message 512 chars — messages longer than 512 chars with different tails will map to same key. So two very different requests get the same tier decision. This is wrong routing behavior, a correctness defect.
   - **Cache is global (ETS table), not keyed by user/API key**. The spec explicitly says non-goal: "按用户差异化策略". But there's a security/QoS angle: one tenant's traffic patterns shape another tenant's routing? Actually the cache key is content-based, so cross-user only if same content. But same system prompt + same user message prefix across different agents → collisions. More importantly, decision should arguably be per-tier-availability: cache stores Tier, then tier→model resolution happens at step ④ (good — resolution is dynamic). That's actually decent design: cache stores tier not model, so model availability changes are handled. But cached tier decisions from a time when judge was configured... if config changes (judge removed), cache still serves old decisions for TTL 300s. Minor.
   - Another critical thing: **cache doesn't include the image/multimodal presence?** Key = {system prefix, last user message prefix, tools presence}. Multimodal content: "末条用户消息前 512" — how are multimodal parts hashed? If image bytes are in content parts, are they part of the hash? Also ctx_tokens isn't in the key: request with 100k tokens context vs 8k tokens — wait, last user message is hashed but total context isn't. A conversation that grows past big_ctx_tokens: cache key is same (system + last user message unchanged across turns?
