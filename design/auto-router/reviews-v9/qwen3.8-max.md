# 复审报告：Janus Auto Router v2.5

## 1. 对上一轮修订的核对

### 1.1 双表写序微竞态（已解决）
**原问题**：先辅后主的写序下，容量清扫可能淘汰刚写入的辅表行，导致主表孤儿逃过 FIFO。
**v2.5 修订**：明确 4096 为软目标；孤儿受 TTL 300s 封顶；每第 64 次清扫附带全表对账删除无辅记录的过期主表条目。
**结论**：**已彻底解决**。将硬上界降级为有界软容量的语义转换非常准确。TTL 提供了绝对上限，`mod 64` 的全表对账以极低的摊销成本（4096 行的 ETS 遍历在 Erlang 中仅需数十微秒）消除了孤儿的长期累积。此设计在正确性与性能之间取得了最佳平衡。

### 1.2 信号量所有权与 caller 崩溃泄漏（已解决）
**原问题**：caller 获取信号量后 spawn worker，若 caller 在 spawn 后、传递 token 前崩溃，信号量泄漏。
**v2.5 修订**：信号量 acquire 移入 worker fun 内部；失败发 `{Ref, skip}` 自退；计数与 worker 生命周期严格绑定；释放写入 `after`。
**结论**：**已彻底解决**。这是 Erlang 并发控制的标准范式。worker 自身持有配额并负责释放，caller 仅作为观察者（monitor），彻底解耦了 caller 生命周期与资源配额的关系。

## 2. 新引入问题审查

经过逐节排查，发现 **一处影响可用性的逻辑矛盾** 和 **两处轻微瑕疵**。

### 2.1 【可用性/正确性】超时不杀 + 长 TTFB = 负缓存击穿保护失效（实质问题）

**位置**：§6.2 执行时序图及代价分析

**问题描述**：
v2.5 决定超时不 kill worker（防止绕过 `after` 导致信号量泄漏），并依赖 gun 的 TTFB 超时（60s）来兜底。但代价分析中存在一个致命的逻辑断层：

1. Caller 设置 `judge_timeout_ms => 1500`（1.5s）。
2. Caller 超时，进入 `after` 分支，**立即写入 30s 负缓存**并计连败，随后返回 `default_tier`。
3. Worker 未被 kill，继续等待 gun 响应。假设 judge 模型在第 10s 返回了成功结果。
4. Worker 执行完毕，发送 `{Ref, Tier}`（此时 caller 已通过排空机制忽略或丢弃该消息），并在 `after` 中归还信号量。
5. **关键点**：Worker 的成功结果**未能写入正缓存**（因为 caller 已经放弃接收并处理该结果，而写正缓存的动作在 caller 端——见 §6.2 时序图 `命中缓存写回`）。
6. 接下来的 30s 内，所有相同特征的请求都会命中负缓存，直接走 `default_tier`，**完全绕过了判分逻辑**。

**影响**：如果 judge 模型偶发抖动（如 2-5s 延迟），不仅当前请求降级，还会触发长达 30s 的负缓存惩罚，导致大量本应被精确路由的请求全部涌入 `default_tier`（通常是 fast 档），可能引发容量溢出或质量下降。

**修复建议（二选一）**：
- **方案 A（推荐，改架构）**：将“写正缓存”的动作移入 worker 内部。Worker 只要在 `after` 之前成功拿到结果，就自行写入 ETS 正缓存。Caller 超时只影响本次请求的返回值，不影响全局缓存状态。
- **方案 B（改参数）**：将 gun 的 TTFB 超时配置为与 `judge_timeout_ms` 一致（或略大，如 2s）。这样超时时 worker 也会因 gun 报错而迅速退出，不会产生“慢成功”。但这违背了“不杀 worker 让其自然有界”的设计初衷。

### 2.2 【文档一致性】规则编号错位（轻微瑕疵）

**位置**：§4.2 规则门表格 vs 变更日志 v2.5①

**问题描述**：
v2.5 变更日志写明：“总量检查（→flagship）先于 prompt 段检查（→big），规则重编号”。但在 §4.2 的表格中：
- 规则 3：`est_total > big_ctx_tokens` → flagship（总量）
- 规则 4：`(prompt_est + tools_est) × 1.2 > big_ctx_tokens` → big（prompt 段）

优先级顺序是正确的（总量确实先于 prompt 段判断），但**变更日志中的“规则重编号”并未反映在历史对比中**（v2.3→v2.4 变更③提到“规则 3b”，暗示原来有 3a/3b 的拆分，现在合并了但未说明原规则 4 是如何变成现在的规则的）。这不影响代码实现，但会导致实施者对照旧版文档时产生困惑。

**建议**：在 v2.5 变更日志中补充一句：“原规则 3b 提升为现规则 3，原规则 3/4 顺延为现规则 4/5”。

### 2.3 【安全性/健壮性】phash2 碰撞下的静默误路由（已知取舍，确认接受）

**位置**：§5 Key

**问题描述**：
使用 `erlang:phash2(..., 268435456)` 生成 2^28 域的 Hash 作为 ETS 键。在 4096 容量下碰撞概率极低（~3e-5），但一旦发生碰撞，两个完全不同的请求会共享同一个缓存决策。由于没有存储原始特征进行二次校验（Anti-collision check），碰撞会导致静默误路由。

**结论**：规格书已明确标注“这是设计选择而非缺陷”，且 3e-5 的概率在 TTL 300s 窗口内几乎不可能造成业务影响。**PASS，无需修改**，仅作复核记录。

## 3. 最终裁定

除 **§2.1（超时不杀导致负缓存击穿保护失效）** 外，其余设计均严密自洽。§2.1 属于影响可用性的实质问题：它使得 1.5s 的超时配置与 60s 的底层兜底之间产生了长达 30s 的负缓存惩罚盲区。

**结论：CONDITIONAL PASS（条件通过）**

**放行条件**：必须采纳 §2.1 的方案 A（Worker 自行写正缓存）或等效机制，确保 Caller 超时放弃等待后，Worker 迟到的成功结果仍能更新全局正缓存，从而避免偶发慢请求引发 30s 的大面积降级。修复此点后，规格书达到生产级标准。
