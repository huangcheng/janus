## 2. Findings

### F1 — Stale clause contradicts itself inside Part 0.2 (mechanical)
Part 0.2 target rule: *"…with **NO UNEXPIRED PASSIVE ROW** (single freshness predicate — …; freshness counts BOTH row sources — the predicate is 'no unexpired row (passive OR probe)'…)"*. The leading phrase is rev-6 wording contradicting its own parenthetical; an implementer could code either reading. **Fix:** delete the "PASSIVE" qualifier from the lead phrase.

### F2 — JSON `probe_skip_total` missing `drained` (schema gap)
Metric: `sched_probe_skip_total{reason=cap|cadence|fresh|drained}` (Part 0.2, rev-7 fold). JSON surface (Part C): `{"cap": int, "cadence": int, "fresh": int}` — no `drained` key, and no other surface for it. The pinned assertion surface must carry every reason. **Fix:** add `"drained": int` to the JSON block.

### F3 — Probe send-fail / ack-miss disposition unpinned (real gap, medium)
`dispatch_probe/2` pins its own draining/dispatchable check, but not what happens when the pinned send fails or the ack misses:
- If it reuses the `janus_http_worker_client` seam as-is, ack-miss triggers **local fallback execution of the probe on the master** — a real (if 1-token) upstream call that measures nothing useful and contradicts "master-issued probes measure the worker path".
- The in-flight probe map is cleared only on *"probe done/error/nodedown"* (Part 0.2). A send-failed probe leaves `{Node => JobRef}` stuck until nodedown or owner restart, blocking all further probes to that worker (≤1-in-flight rule).

**Fix:** pin in Part 0.2: probe send-fail AND ack-miss ⇒ abort, clear the in-flight entry, count (`probe_skip{send_fail}` or fold into an existing reason), **no local fallback for internal jobs**. Add the matching eunit line (also covers the F12 gap: no eunit currently exercises `probe_skip{drained}` or send-fail).

### F4 — Post-adopt recovery rests on an unnamed re-hello mechanism (verify-at-implementation, high)
Adopt prunes ALL `sched_workers` rows because the new owner has no pool records, so *"every worker must RE-HELLO post-adopt (dist connections survive; sticky sessions re-hello)"*. If the shipped hello is connect-time-only, a pool-owner restart empties the pool **until workers are restarted** — every pick falls back locally. The spec asserts the re-hello exists but never names the shipping seam (heartbeat interval / sticky keepalive module).
**Fix:** (a) verify + name the re-hello trigger at implementation start (like the done/error map-shape verification); (b) extend eunit 4's adopt cycle: adopt → worker re-hello → snapshot rebuilt → pick dispatches again. Currently no test covers dispatchability recovery after adopt.

### F5 — Live re-check behavior on a MISSING `sched_workers` row unpinned (small)
Matters in the ≤250 ms post-adopt stale-snapshot window (snapshot lists candidates; `sched_workers` is already empty). **Fix:** one sentence — missing row ⇒ treat as drained/refuse (safe direction).

### F6 — Orphan `sched_reserve` rows for dead nodes (cosmetic, small)
Rollback racing nodedown re-inserts `{Node, 0}` via the Default tuple; the corrective write heals it to 0, but the row then lingers until rejoin or next adopt (no further nodedown will delete it). **Fix:** pin the 30 s reconcile to also delete `sched_reserve` rows for nodes absent from pool records.

### F7 — Inaccurate badarg rationale (cosmetic)
The fold's justification — *"an atom-vs-number guard comparison would badarg"* — is wrong: in Erlang term order `Number > infinity` simply evaluates `false` (numbers < atoms), in guards and expressions alike; no badarg occurs. The pinned behavior (skip the comparison when `capacity =:= infinity`) is still correct and belt-and-braces (it also prevents `false`-by-term-order accidentally meaning "infinity never trips" for the wrong reason). **Fix:** reword the rationale; keep the skip.

### F8 — `SampledAtMono` provenance implied, not pinned (one sentence)
Wire shape (done/error carry only `rtt_ms`) forces the master to stamp `SampledAtMono` at ingest — which is the only sane choice, since per-VM monotonic clocks are incomparable across nodes (Part 0.9). State it explicitly so nobody adds a worker-side timestamp key later. Also note the fold's "closes the concurrent piggyback-vs-cold-start race" is really about *out-of-order delivery*, since all writes serialize in the pool gen_server (single-writer pin holds).

### F9 — `JANUS_SCHED_GEO_TEST_HOSTS` resolution seam not named (small)
Part 0.1 pins the boot-check effect; Part A.1 (`janus_geo:resolve_host`) never says the test-host map is consulted *before* DNS/mmdb. Gate 13.3b depends on it. **Fix:** name the seam in A.1.

### F10 — Gauge cap mechanism (implementation note)
`sched_rtt_ms` capped to 64 label sets: Prometheus client registries keep label sets until explicitly deleted, so the cap requires deleting evicted label sets, not just stopping writes. One clause in Part C.

### F11 — Doc hygiene (mechanical)
- TF-13.2–13.6 additions imply a `../janus-dashboard/docs/TEST-FLOWS.md` update (AGENTS.md: the gate "grows with TEST-FLOWS.md"); not listed in Part D.
- `geo_match_total{none}` conflates "pinned pick" with "no geo comparator" (pinned picks emit `none`). Harmless for the ≥-style gate assertions; one clarifying sentence suffices.
