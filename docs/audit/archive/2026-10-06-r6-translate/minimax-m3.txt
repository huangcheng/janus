**Verdict:** GO WITH FIXES — C1-C6 contracts and ship unit 1.9 are sound, but C1/C4 commit semantics, C2 chat-error wording, and 1.8b cache-token sourcing need tightening before Phase 1 deploys.

**Critical risks:**

1. **C1/C4 commit boundary ambiguity.** C1 says skeleton is required; C4 says commit = first DATA frame. OpenAI chat's first chunk is `{"role":"assistant","content":""}` — is THIS the commit point or the first content delta? If the former, the failover window is ~0 and lazy emission is dead. Specify: commit = first non-empty content frame; role-only preamble is a skeleton emission that CAN be retried.

2. **C2 chat-terminator wording is wrong.** "Error frame REPLACES the success terminator" — `[DONE]` is chat's transport terminator and STAYS after the error JSON (the plan's own example shows this). Rewrite as "replaces the success frame SET (role/finish/usage); `[DONE]` always follows."

3. **1.8b cache_read_input_tokens has no source rule.** Anthropic→chat translate sets it to 0 (silent billing loss). Document per-protocol-family source (anthropic prompt-cache header only; chat/responses = 0).

4. **C5 synthesized id uniqueness is mis-stated.** "Non-repeating across attempts" is impossible by design — per-attempt fresh `sse_st` resets the counter, so attempt-2 ids collide with attempt-1. Should be "unique WITHIN an attempt." Add prefix table for responses target (resp_/msg_/fc_/item_).

5. **3.2b error-code duplication.** `n>1` → responses provider is already rejected by 1.5 (cross-protocol). Use one code (`n_unsupported`), not two.
