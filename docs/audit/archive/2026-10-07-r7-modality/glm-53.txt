# Audit — rev 7

**1. Verdict: GO WITH FIXES** — converged on wire/usage/video lifecycle, but TTS commit point is stated two contradictory ways and the sync-hold "accept" signal is undefined — both on the spend-discipline critical path.

**2. Critical risks**
- **TTS commit contradiction (spend-critical):** A6's opening says "TTS = first audio byte"; A6's `commit_point/1` enumeration and the Contracts section say `upstream_accept`. M2.1's "pre-first-byte failover window" is the stale third variant. Post-accept/pre-first-byte failures are answerable as JSON (nothing sent yet, headers included) — but only if ONE commit point survives.
- **Sync-hold accept is undefined for blocking one-shot upstreams.** Native sync endpoints emit no 2xx until completion. If accept = response headers, ≥1-per-10s heartbeats violate lazy emission (written pre-commit); if accept = request-sent, an upstream 400 becomes a mid-stream `failed`, contradicting "pre-accept failures answer plain JSON". Pin: synthesized heartbeats are gateway-owned and non-committing; commit = first upstream response byte.
- **Writer-owned finalization untested:** idle_timeout/client-reset killing the handler is the hardest path (monitor → usage writer) and no E2E step exercises it.
- **ASR 429 vs failover loop:** node-local admission rejects must bypass the failover loop (retrying another provider frees no slots); plan doesn't say so.
- **Secret bootstrap:** followers "block/poll" with no timeout — a wedged leader hangs the fleet's boot.

- Task IDs listed M3.2, **M3.2c**, **M3.2b** — cosmetic ordering noise in a plan this audited.
