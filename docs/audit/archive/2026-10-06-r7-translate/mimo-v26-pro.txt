**2. Critical risks**
- **C1 vs C4 contradiction (fatal for implementers):** C1 says the terminator is emitted "exactly once per COMMITTED response (pre-commit retries emit nothing client-visible)" and C2 says pings "never commit the stream"; yet C2/C4 also say a failure with zero prior data frames "owes a target-format error event + terminator + usage row (headers already went out)" — i.e. an uncommitted stream emits terminators after all. Pick one rule: pre-commit failure emits error+terminator once attempt exhaustion is final; pre-commit *retry* emits nothing. State it once, in C4.
- **1.5 knob ambiguity:** "the non-stream reject rides in 1.9's commit (before the flip, behavior is unchanged)" only holds if `n_unsupported` itself is knob-gated. If it fires on deploy, rolling out 1.9 changes default behavior — the exact thing 1.9 forbids. Say explicitly: reject active ⇔ knob on; e2e asserts both regimes (it claims to, but the gating is unstated).
- **Failure-usage under translation:** C3 merges anthropic input+output into one event, but C2 says a `message_delta` "before an error still counts" — when error *replaces* `message_stop`, where does merged usage ride for →anthropic (no `message_delta` may precede `error` legally)? Specify: on error paths, usage goes to the usage row only, never synthesized into a terminal success event.
- **request-grammar fidelity:** chat `tool_calls` with `finish_reason` absent/null (mid-stream cut) and anthropic `tool_use` with empty input `{}` (zero-arg tools) are unspecified; zero-arg tools break "accumulate args → decode at close" (empty binary is invalid JSON).
