2. **Critical risks**
- **API filter bug (highest):** `handle_usage_events` uses `maps:filter` with a predicate returning `{true, {key_id, …}}` — non-boolean → `badarg` → 500 whenever `key_id`/`model_id` is present. The plan's own Step-3 curl (`?key_id=1`) and the SPA drill-down hit this. Even if it didn't raise, the resulting `{<<"key_id">> => {key_id,V}}` shape never matches `recent_filters`' `{key_id, V}` tuple pattern — filters would be silently ignored.
- **Read-path badmatch:** `totals/series/breakdown/recent/p95` all do `{ok, Rows} = q(...)`; `q/2` returns `{error,_}` on any dialect/DB failure → caller crash, contradicting the "exception-safe" contract. Postgres branches (`percentile_disc`, `to_char` quoting, `GROUP BY` alias) are only verified on an optional lane — untested-dialect 500s are likely on first Postgres ship.
- **SSE fidelity:** good — 4KB head covers `message_start`, 16KB tail covers terminal chunks; residual caveats (per-chunk-delta providers, >4KB pre-usage preamble) are documented.
- **gen_server buffer:** per-drop `logger:warning` at cap is an unbounded log flood; mailbox growth under a stalled DB is accepted and surfaced — fine.
- **latency/p95:** p95 split is correct; `avg_latency_ms` still mixes stream/non-stream (residual round-1 finding; page doesn't show it, API does).
- **Migration/retention/FK/hot path:** fine (31d>30d, batched sweep, `IF NOT EXISTS`, SET NULL/LEFT JOIN consistency, negligible per-chunk cost).
