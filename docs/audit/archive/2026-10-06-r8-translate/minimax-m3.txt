**Critical risks:**

1. **Lazy emission vs `response.created`**: C1 lists it as the first skeleton event; C4 forbids skeleton emit before first upstream event. Specify: `response.created` is synthesized on first upstream arrival (clients need it early; omitting breaks them; emitting eagerly breaks C4's failover window).

2. **Header-flush pre-commit retry**: C4 case (a) allows retry after headers flushed but before DATA. Client has already received 200 + `Content-Type: text/event-stream`. A retry's different body over those headers can mis-handle on some parsers. Brief note needed.

3. **Synthesized id prefixes inconsistent**: C5 says `jresp_`/`jmsg_`/`jfc_`/`jitem_`; 2.1 says `resp_`/`msg_`/`fc_`/`item_`. Pick one (the `j`-prefix per C5's collision intent).

5. **C2 wire shape for synthesized errors**: Plan defines internal struct `{type,code,message}` but no wire spec for cross-protocol errors (chat top-level `error`? Anthropic full envelope? Responses `response.failed.error` shape?).
