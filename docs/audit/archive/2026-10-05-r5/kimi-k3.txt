**1. Verdict:** GO WITH FIXES — sound architecture reusing generation-poll, but the traffic-write contradiction, time-dependent catalog filter, and key-vs-model cooling confusion must be fixed before implementation.

**2. Critical risks**
- **Probe blowback:** 786 requests at concurrency 5 will trip provider anti-abuse/rate-limits on exactly the keys being measured; some providers (Ark) throttle account-wide, poisoning production traffic mid-probe. No per-key rps cap, only concurrency.
- **Classification false-negatives:** the deny regex is English-text-centric; DashScope/Ark return structured `error.code` (often non-English messages). Worse, the `input_shape→ok` rule fails *unsafe*: any non-matching 400 from a genuinely unentitled model marks it `ok`.
- **Latency amplification:** worst case 3×(connect+TTFB). Under Cowboy's 300s `idle_timeout`, but agent clients commonly time out at 60–120s; failover "succeeds" after the client hung up.
- **Retry storms:** during a provider-wide 429 event, every request now multiplies upstream QPS ×3 precisely when the provider is limiting — 429 rate-limit should fail over *at most once*, like 5xx.
- **Catalog drift:** the bundle SQL filters `checked_at > now() - interval '7 days'` at *fetch* time — two gateways polling the same generation at different times get different matrices; rows silently expire deny→eligible.
- **Key rotation:** rotation = new key id = empty matrix = all-unknown = blind LB again until re-probe; spec never says rotation triggers probing.
- **Streaming boundary:** correctly drawn at first client byte, but 200-status-then-error-chunk (upstream error event mid-stream) is unaddressed.

**3. Contradictions / stale claims**
- A.1 says `source='traffic'` rows "are written by the gateway (Part C)" — violates the stated boundary (gateway never writes dashboard tables); A.3 correctly says the dashboard refresher folds usage rows. Fix A.1.
- B ships `ok` rows in the bundle, then catalog discards them — pure waste across 786+ rows × nodes.
- C.1 "`balance`… become deny-refreshable" vs A.1 "retryable-later… until refreshed" — refresh restores `balance`, not `deny`; semantics unclear.
- C.1 `note_key_failure` is key-level cooling, but a model-scoped deny would cool the key for *all* models — contradicts the per-(key,model) premise.

**4. Missing requirements**
- Entitlement is per (key, **endpoint**, model) — zhipu coding-plan keys fail on the wrong base_url; the PK omits endpoint.
- Generation-bump granularity: per-row bumps on a 786-row probe = reload storm; must be one bump per batch.
- 401-abort disposition: is the key auto-disabled in LB or only "surfaced"?
- Double-billing acknowledgment: retrying a non-idempotent completion after upstream accepted-but-5xx charges twice.
- Model-name aliasing: usage rows record routed model name; matrix keys by listing name — mapping unspecified.

**5. Architecture notes**
- ETS swap is atomic per generation, but the SQL TTL makes bundle content time-dependent — compute the cutoff once at bundle build and pin it.
- Usage-row-per-attempt is fine (janus_usage is async) but needs an `attempt`/`failover` flag or passive learning can't distinguish retried failures.
- Probe runner and traffic refresher race on the same PK — enforce last-write-wins in SQL (`ON CONFLICT … WHERE excluded.checked_at > …`), not app-side.
- 429 dual meaning is provider-specific; text matching will misclassify rate→balance and needlessly exclude keys until next probe.

**6. Top 5 edits**
1. A.1: only the dashboard writes `key_entitlements`; gateway writes usage rows only.
2. Scope matrix to (key, endpoint, model); classify on structured provider error codes with a per-provider table, not one regex; make non-matching 400 default to `unknown`, not `ok`.
3. Ship deny/balance only; pin TTL cutoff at bundle build time.
4. Add per-(key,model) eligibility skip without key-level cooling; 429-rate fails over at most once.
5. Probe safety: per-key rps cap, cost estimate + confirm above N listings, single generation bump per batch, trigger probe on key rotation.
