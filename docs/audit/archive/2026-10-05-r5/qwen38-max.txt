**1. Verdict**
GO WITH FIXES — sound architecture, but the traffic-learning path is underspecified to the point of repeating the bug it claims to fix, and the retry loop's edge behaviors are undefined.

**2. Critical risks**
- **Probe blowback:** 786-request sweeps at concurrency 5 will trip provider RPM limits; 429→"skip, throttle" has no backoff/jitter spec. Repeated sweeps after each sync can keep a key rate-limited for real traffic.
- **Classification false-negatives:** deny detection is an English regex. Localized/variant messages (DashScope, zhipu, Ark) fall through to "400 not matching regex → `ok`", marking denied models eligible — the exact uni-api failure, inverted.
- **Failover latency amplification:** worst case 3 × 60s TTFB = 180s; client-side timeouts will orphan retries mid-flight (orphaned upstream calls not discussed).
- **Retry storms:** no backoff means N concurrent clients × 3 attempts = 3× load on an already-rejecting provider; shared-account key pools share rate limits, so 429-failover can amplify rather than escape.
- **Reload races:** carriers are separate SELECTs; a generation bump mid-bundle mixes matrix and routes. ETS rebuild atomicity vs concurrent `pick` reads is asserted, not specified.
- **Staleness on rotation:** secret rotated in place (same id) leaves stale deny rows blocking the fixed key up to 7 days.
- **Streaming boundary:** "first byte" is ambiguous — if status/headers are flushed, failover is already impossible; spec must say *no response bytes including status line*.

**3. Contradictions / stale claims**
- Carrier SQL ships `ok` rows though Part B says only deny/balance are kept — filter them in SQL.
- A.3 folds "status 400/404 with the recorded error shape" into deny, but nowhere is the usage schema extended to record error body/code — usage rows have only status, so this either can't classify or must guess (input-shape-400 → wrongly denied).
- "Compare `checked_at`" for ok/deny ordering uses row-write time, not event time — out-of-order usage polls can still downgrade `ok`.

**4. Missing requirements**
- Usage-row schema addition: upstream `error_code`/text (prerequisite for A.3).
- Behavior when **zero eligible keys** remain after pre-filter (fast 503 shape? fall back to least-bad key?).
- How the loop knows "more eligible keys remain" — `pick_*` returns one route; the candidate-count/LB API change is unlisted.
- Upsert `ON CONFLICT` policy for probe-vs-traffic write races.
- Key-secret update must invalidate its entitlement rows.
- Usage-aggregation semantics: 2–3 rows per failed request inflates request counts/cost views.

**5. Top 5 edits**
1. Require upstream error text/code in usage rows; without it A.3 is unverifiable.
2. Ship only deny/balance in the bundle; mandate single-snapshot fetch + atomic ETS swap.
3. Define zero-eligible-key fast path and the pick-API extension for remaining-key awareness.
4. Conflict rule: last-write-wins on *event* timestamp; invalidate matrix on key secret update.
5. Add per-attempt backoff (honor Retry-After on 429) and redefine failover boundary as "no response bytes (incl. status line) flushed".
