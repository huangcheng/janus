## 1. Verdict
**GO WITH FIXES** — the phase/knob structure is sound, but several cross-cutting stream contracts are internally inconsistent and two "corpus" fixtures are secretly synthetic.

## 2. Critical risks
- **Terminator rule self-contradicts.** C1 says terminator is "emitted exactly once per COMMITTED response," but C4(b) and the C2 zero-data-frame note emit a terminator for an *uncommitted* all-attempts-fail response. Reword to "once per terminated response."
- **Overlapping caps, no memory budget.** C5 has 4MiB total content *and* 1MiB total args with undefined precedence, while 3.4 soaks 50 concurrent × 4MiB ≈ 200MiB/stream-set unaddressed.
- **Lazy-emission trigger undefined.** C1/C4 gate skeleton emission on "CONTENT-bearing" events; unclear whether a role-only delta or a `tool_use` start with no args qualifies. Combined with C5's zero-arg tool, the empty-accumulation → `{}` decode rule is missing (empty string is not valid JSON).
- **Fixture realism violated by 1.0 itself.** "one >64-calls transcript (cap proof)" and "mid-stream TRUNCATED" are hand-synthesized; C6 forbids hand-invented frames. No real provider emits >64 calls.
- **Failure usage lost to clients.** C2 routes usage to the usage row only; the →chat usage-only chunk never appears on failure, so billing-visible clients see null tokens.

Event mapping should be a per-(source,target) **data table**, not branching code — makes 1.1/2.1/3.2 testable identically. Canonical error struct needs a `retryable` flag. `sequence_number` monotonicity must be asserted per target stream, not globally.
