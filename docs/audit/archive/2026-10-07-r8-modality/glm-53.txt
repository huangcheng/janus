## 2. Critical risks
- **Pass-through vs 64MiB cap (live contradiction):** Contracts says video `completed` b64 "passes through under the response rule **regardless of size**"; the Images section says the IMAGE/VIDEO JSON buffering cap (64MiB) → `failed(response_too_large)`. An implementer can satisfy either; pick one.
- **Secret bootstrap owner conflict:** R7 summary says the **dashboard backend** owns bootstrap ("no gateway leader election"); M3.1b body still says "the **migration LEADER** generates… followers block/poll" — i.e., gateway nodes racing. This is the exact race R7 removed.
- **M3.2b vs M3.4 soak contradiction:** M3.2b says "Gate asserts a >310s mock video" while M3.4 says the >310s check is a documented **manual soak** and CI uses 30s/31s. The M3.2b sentence is stale (pre-R-fix) and would hang the CI gate.
- **Sync-video commit observable ambiguity:** A5 defines accept as **first upstream response byte**; A6 files sync-video under `first_media_byte` (client SSE event). They coincide under lazy emission, but the shared loop must be told which stream it watches (gun vs client socket) and `commit_point/1` returns one atom.
- **270s zero-byte pre-accept window:** with heartbeats post-commit only, clients/proxies (nginx 60s `proxy_read_timeout`) will cut sync holds long before 270s first byte. Undocumented practical limit; either document a low realistic sync budget or push slow providers to async.
- **ASR admission bypass:** header-time check keys on `content-length`; chunked multipart uploads evade it. Specify reject-or-count behavior.
- **Units double-count:** video per-attempt rows plus the one terminal jvid row both may carry `units=video_seconds`; dashboard sums inflate unless attempt rows are pinned `units=NULL`.
