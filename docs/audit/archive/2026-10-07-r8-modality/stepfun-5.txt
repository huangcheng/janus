## Critical risks
1. **Async-video row model is ambiguous.** M1.1 says "existing failover machinery unchanged" (per-attempt rows) AND "usage_events receives exactly ONE terminal row per jvid." Both in the same table = double billing on the dashboard unless attempt rows are suppressed for video. Failed jobs pre-terminal (provider compute consumed, no usable result) get no defined row.
2. **Usage-row atomicity has a crash window.** CAS `UPDATE video_jobs … WHERE status='pending'` (+ affected-rows) followed by a separate INSERT loses usage if the writer dies between them; a later poll sees non-pending and never inserts. "Single-statement" must mean a true CTE on both dialects, or the sweep must reconcile.
3. **ASR admission assumes content-length.** Chunked/absent CL has no rule; the 25MiB×4-slot memory bound is undocumented; ASR's `commit_point` is missing from A6's enumeration (presumably `pre_2xx`); slot retention across failover attempts unstated.
4. **M1.0c changes the shared loop's blocked/commit predicate for chat too** — zero chat regression steps in the M1.3 gate (the prompt's backward-compat concern).
5. **Computer-use is route-dependent but detection seems post-LB.** Reject-if-misfortune instead of filtering to anthropic-native routes when `computer_*` tools are seen.
