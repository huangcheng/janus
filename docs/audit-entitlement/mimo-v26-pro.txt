**1. Verdict:** GO WITH FIXES — the design is sound and failure-mode-driven, but several internal contradictions (healing priority, fail-open semantics) and billing/backfill gaps must be resolved before implementation.

**2. Critical risks**
- **Probe blowback:** 150ms spacing × 262–786 models still shares RPM with live traffic; the 30s pause-on-429 is reactive, not preventive. `max_tokens=1` probes on metered keys cost real money at scale (5000/day default = DashScope ×3 keys ×2 days of bootstrap).
- **Deny-regex false positives:** anchoring helps, but `product.*未开通` is unanchored on one side and codes/messages-scoping is SQL-shape, not enforcement — an echoed prompt containing the phrase still misclassifies if any provider nests it in `code`.
- **Failover latency vs idle_timeout:** worst case = 45s budget + 60s TTFB + 30s body-cap + jitter + *unconditional first call* ≈ 140s+ against 300s idle_timeout — fine, but 30s clients abandon mid-failover and burn quota silently.
- **Retry storms:** N concurrent requests × 4 keys × (1 + 3 + 1 provider + 1 pool_reuse) = up to 7 calls/request; the 429 rate-class "no cooldown" default (missing codes table) is exactly the storming path it claims to prevent.
- **Reload races:** entry-snapshot threading is right, but `pool_reuse` picking "cooldown-EXPIRED attempted keys" and mid-loop key deletion are specified loosely ("no-op in janus_lb") — verify against actual janus_lb semantics.
- **Balance starvation:** key-scoped canary assumes `key_scoped_balance=true`; no default given, and per-row fallback re-probes 262 models for one top-up.
- **Key rotation:** delete-all-rows + bump is right, but "row-less = eligible" means a rotated-broken key re-poisons traffic until the bootstrap probe lands.
- **Streaming boundary:** 200-then-stall committed at `stream_reply` is stated; the error-status `collect_drain` retryability is asserted, not proven.

**3. Contradictions / stale claims**
- A.2: broken-row healing "priority ABOVE balance" vs A.4 "balance > deny > ok" and test-agnostic.
- C.1 fail-open ("ignore matrix for one attempt") vs "at most one fail-open attempt" — what happens when the fail-open attempt fails retryably? Undefined.
- A.1 "key insert inserts unknown rows lazily" vs A.4 trigger 2 "key insert → bootstrap probe".
- Legacy backfill `attempt=1, is_terminal=true` — legacy rows have no `request_ref`; crash-marking lookups on NULL undefined.
- "Provider retry is a reserved slot (total ≤ max_attempts+2)" vs pool_reuse "OUTSIDE the key budget" — is the true bound +3?

**4. Missing requirements**
- `key_entitlements`/`probe_budget_counters` retention & day-rollover (timezone); `entitlement_codes` regex length cap value; probe concurrency/RPM measurement method; failover feature-flag/rollback; attempt-index semantics for provider/pool_reuse rows in the "highest attempt" exhaustion rule; pagination for `GET /api/entitlements`; per-operator probe quota.

**5. Architecture notes**
- Entry-snapshot generation threading correctly protects ETS atomicity against mid-request reloads; good.
- `is_terminal`-only billing is right, but non-terminal rows entering usage aggregates need the dashboard-side filter specified as a migration invariant.
- Dashboard-writer ownership is convention-only; the gateway carrier being read-only SQL is the real guarantee — keep both.
- 429 dual-meaning via `entitlement_codes` is the right single-sourcing; the empty-table default (all rate-class) trades safety for fail-open — document the balance-dead-key storm window.

**6. Top 5 edits**
1. Reconcile healing priority: broken > balance > deny > ok everywhere (A.2 vs A.4).
2. Specify fail-open-after-fail-open: terminal with the last error; forbid loop continuation.
3. Define `attempt` numbering for provider-retry/pool_reuse rows and fix the exhaustion "highest attempt" rule.
4. Give `key_scoped_balance` a seed default (true for DashScope/Ark/zhipu) and bound the canary.
5. Add tests: empty-codes-table fail-open default; generation-snapshot consistency mid-request; NULL `request_ref` backfill.
