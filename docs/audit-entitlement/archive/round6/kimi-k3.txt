## 1. Verdict
**GO WITH FIXES** — sound architecture, but budget-accounting inconsistency, an unpriced traffic-refresher feedback loop, and a streaming drain boundary gap need resolving before implementation.

## 2. Critical risks
- **Probe cost blowback**: addressed (daily budget, advisory lock, 429 backoff) but the 150ms spacing × 262 models × parallel-2 keys still means ~20min/provider; single-flight "per provider" doesn't bound cross-provider fan-in on rate pools shared with live traffic.
- **Deny-regex vs input-shape**: the `ok+input_shape` fail-open is right, but `escalated=true` rows are dropped from healing with only "deny-shaped traffic evidence (once E.1 lands)" as re-admission — E.1 is a prerequisite, so escalated rows are permanently dead in v1.
- **Failover latency vs idle_timeout**: ceiling math (180s) is coherent, but a 45s default budget against 30–60s client budgets means callers abandon mid-failover often; that's acknowledged but the retry still burns upstream quota for abandoned work.
- **Retry storms**: no pool-level breaker is accepted as "existing cooling suffices," but a provider-wide 429 burst across N keys now generates N× retries where today it generated N failures; RATE-class cooldown of only `max(Retry-After,10s)` on the *picked* key doesn't protect *other* requests from hammering the same pool.
- **Balance-key starvation**: canary probe updating ALL balance rows from one model's outcome is aggressive — a model-specific quota error (429 on model X only) will wrongly clear balance on the other 261 rows.
- **Key rotation staleness**: row-less = eligible is correct fail-open, but the probe-bootstrap queue has no latency SLA; a swapped-to-broken key fails over per-request for up to a full queue cycle.
- **Streaming first-byte**: error-status streams take collect_drain, but the drain's body-cap/TTFB interplay with the 30s/64KB classification cap is asserted, not specified — a slow-dripping error stream can sit between the two timeouts.

## 3. Contradictions / stale claims
- A.4 says "`JANUS_PROBE_MAX_CALLS` is a per-provider **DAILY** budget"; A.2 defines it as a **per-batch** hard stop with a separate `JANUS_PROBE_DAILY_CALLS` daily knob. Two different knobs, one name.
- A.3 traffic refresher is "ok-only" yet A.1's timestamp-guard discussion describes traffic rows demoting — vestigial from an earlier draft.
- C.1 says non-deny 400 gets "ONE failover attempt, then terminal" but D-flow 8 ("input-shape → NO retry, immediate error") contradicts it — the spec classifies `no permission` as input_shape, so flow 8 as written fails under C.1's own rules.

## 4. Missing requirements
- No max row-count / cleanup policy for `key_entitlements` (deleted listings leave orphan rows forever).
- No concurrency cap on the failover loop across requests (only per-key cooling) — the retry-storm guard.
- Probe evidence for `broken` (`__key__`) has no healing path stated — who re-probes a key after secret is confirmed good? (Answer exists via rotation, but manual "key fixed provider-side" is unhandled.)
- `entitlement_codes` carrier: no versioning/migration path when dashboard adds providers gateways don't know.
- No spec for what happens when `usage_events` error_code (E.1) arrives mid-deployment — mixed old/new rows.

## 5. Architecture notes
- ETS single-generation snapshot per dispatch is correct and matches existing catalog invariants.
- `is_terminal`-only billing is right, but the 300s crash-backfill grace means dashboards show transient double-counts for up to 5min — worth stating.
- Dashboard-writes/gateway-reads ownership is clean; timestamp-guard with one DB clock is sound.
- 429 dual-class via codes table is the right single-sourcing; empty-table fail-open-to-rate is the correct default.
- Attempt accounting (`1 + max_attempts`, reserved provider slot) is now off-by-one-free — good.
- Knob delivery via settings→persistent_term honors the repo invariant.

## 6. Top 5 concrete edits
1. Rename per-batch cap to `JANUS_PROBE_BATCH_CALLS`; keep `JANUS_PROBE_MAX_CALLS` as the daily budget (or vice versa) — one name each, fix A.4.
2. Rewrite D-flow 8 to match C.1: input-shape 400 → exactly one failover attempt, then terminal; assert the single attempt, not zero.
3. Scope the balance canary: update only rows whose model family matches the canary's 429 class, or require canary success on a *bound* model before clearing all.
4. Give `escalated` rows a v1 re-admission path (e.g., monthly re-probe or manual UI reset) instead of waiting on E.1.
5. Specify the error-stream drain boundary: classification cap (30s/64KB) must subsume the collect_drain timeouts for `Status >= 400`, with a single named constant.
