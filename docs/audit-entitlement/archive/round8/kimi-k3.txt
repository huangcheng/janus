# Audit: Key Entitlement Matrix + In-Request Key Failover

## 1. Verdict
**GO WITH FIXES** — the design is coherent and fail-open in the right places, but it ships one internal contradiction (broken-key row), an undefined generation-bump path on secret rotation, and an over-broad balance-canary assumption.

## 2. Critical risks
- **Balance is not always key-level.** A.4's canary ("one probe updates ALL balance rows") assumes key-scoped quota; zhipu 1113 is a 资源包 code and can be model/endpoint-scoped. One canary on a depleted model can wrongly re-admit (or keep excluding) 261 others. Spec asserts key-level without evidence.
- **Probe cost vs rate-limit blowback:** mitigated (advisory lock, pacing, daily budget, 25% healing reserve). Solid.
- **Deny-regex false positives:** well handled (anchored, `no permission` explicitly non-deny, message-field scoping). Residual: an unseeded provider's deny wording costs one wasted retry *per request forever* (C.1 unclassified→one retry) until someone hand-edits `entitlement_codes`; no feedback automation, only "usage row is feedback".
- **Failover latency vs idle_timeout:** ceiling math (180+60+30=270<300) holds but leaves 30s margin; the 45s default silently abandons 30s-budget clients — documented, accepted.
- **Retry storms:** no pool-level breaker (explicitly deferred). With per-key cooling only, a burst on a 2-key pool with one rate-limited upstream multiplies upstream calls ~4×. Acceptable v1, but say so in C.1.
- **Matrix/reload races:** entry-snapshot threading is correct. Fail-open pick reusing the same snapshot is correctly specified.

## 3. Contradictions / stale claims
- **A.1 vs A.2:** A.1 says probe-abort 401/403 *writes* the `__key__` broken row; A.2 says "leave prior rows untouched" with no write step. Who writes `__key__`, and does it bump generation?
- **Naming:** `retry_provider` implies cross-provider, but "cross-provider failover" is out of scope and the reuse rule ("coolest attempted key") is intra-pool. Rename or clarify.
- Counters named `janus_entitlement_failopen` (B) vs `entitlement_failopen` (C.1).

## 4. Missing requirements
- **Generation bump on secret update/row deletion** — A.1 deletes all rows but only probe batches bump; a fixed key stays `broken`-skipped on gateways up to 24h.
- **Orphan cleanup:** rows for listings removed by re-sync never expire (deny/broken TTL helps, but there's no delete-on-catalog-removal; unbounded growth).
- `failover_max_attempts` has no validation range (only budget ceiling is validated).
- Billing: retroactive `is_terminal` backfill (crash path) mutates already-aggregated windows — no statement on how dashboards handle the flip.

## 5. Architecture/design notes
ETS snapshot-per-request and PT knob delivery conform to repo invariants. Dashboard-owns-writes / gateway-reads-carrier is clean, and the missing-table fail-open is right. The 429 dual-class single-sourcing in `entitlement_codes` is the strongest part of the spec. Attempt accounting (retries-after-first, reserved provider slot outside key budget) is off-by-one-proof. Usage-row multiplication is bounded and billing semantics (`WHERE is_terminal`) are sound except the retroactive-flip caveat above.

## 6. Top 5 concrete edits
1. Fix the `__key__` contradiction: state explicitly in A.2 that abort upserts `(__key__, broken)` and bumps generation.
2. Require `bump_generation` on key secret update (row deletion must propagate).
3. Qualify the balance canary: update all rows only when the provider's balance class is confirmed key-scoped in `entitlement_codes`; otherwise per-row re-probe.
4. Add catalog-removal cleanup (delete entitlement rows for vanished listings at sync) and validate `failover_max_attempts ∈ [0, N]`.
5. Rename `retry_provider` (e.g. `retry_pool_reuse`) and unify the fail-open counter name.
