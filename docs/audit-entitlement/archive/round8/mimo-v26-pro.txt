**1. Verdict:** GO WITH FIXES — the design is unusually complete, but several internal contradictions (TTL ownership, fail-open scope, broken-key recovery) and one starvation path must be resolved before implementation.

**2. Critical risks**
- Probe cost: 786-call DashScope bootstrap vs 5000/day shared budget; healing's 25% reservation is enforced only by counters, not per-trigger isolation at the queue level.
- Deny-regex false positives: fail-open default is right, but codes-table regex rows are written via admin API with **no validation requirement** — one bad regex silently bricks classification fleet-wide.
- Failover latency: 45s default + 60s TTFB + 30s body-cap = 135s; fine vs 300s idle_timeout, but most clients (30–60s) abandon mid-loop, wasting upstream quota on every exhausted failover.
- Retry storms: 100–300ms jitter is negligible; with all-broken pools every concurrent request multiplies upstream calls by ≤ max_attempts+2; missing codes seed defaults 429→rate-class (retry, no cooldown) — the worst case for storms.
- Reload races: per-request generation snapshot is correct; but **secret-update row deletion must bump generation** or gateways keep stale deny rows for a rotated key.
- Balance starvation: canary probe "any model" can return deny/input-shape and wrongly overwrite all balance rows — canary must be a known-ok model.
- Rotation staleness: `__key__` broken rows have no recovery path — never re-probed, so broken keys bounce between broken and eligible forever.
- Streaming boundary: error-status streams take collect_drain, which may discard the body the classifier needs.

**3. Contradictions / stale claims**
- A.1 "consumers enforce [TTL] by checked_at" vs Part B "SQL is the ONLY TTL enforcement point."
- A.2 401/403 "leave prior rows untouched" vs A.1 "writes status='broken' `__key__`."
- "in-process lock" vs "advisory lock is the single mechanism."
- sqlite carrier variant is shipped yet declared illustrative/never-used — delete it.
- Fail-open pick "any non-cooling key" vs "known-broken keys skipped entirely" — are broken/deny keys eligible in the fail-open pick?

**4. Missing requirements**
- Fail-open attempt's place in the attempt budget (inside max_attempts or the +2?).
- Generation bump on entitlement row deletion (rotation).
- Canary model selection rule; broken-key re-probe policy.
- Codes-table write validation (regex compile, outcome enum).
- Single-key pool edge: provider-retry "never the one that just failed" is unsatisfiable.

**5. Architecture notes**
- ETS atomic rebuild + snapshot threading is sound; deny map size is bounded since `ok` never ships. Per-attempt rows with `is_terminal` gating billing is correct; non-terminal 200s are impossible, so A.3's promote-only rule is safe. Write ownership (dashboard-only) is cleanly enforced; the gateway's read-only classifier via carrier is the right split. 429 dual-class needs the codes seed BEFORE any gateway traffic, else balance keys thrash. Knob delivery via persistent_term matches the repo invariant; ceiling validated at write time — good.

**6. Top 5 edits**
1. Fix the TTL contradiction: state the carrier SQL is authoritative and A.1's "hard rules" bind the dashboard only.
2. Add "secret/key row deletions bump generation" to A.1.
3. Specify canary = first `ok`-row model; add broken-key expiry→re-probe.
4. Define fail-open/broken-key membership and fail-open's budget slot in C.1.
5. Mandate codes-table write validation + ship the seed in the same migration as Part C.
