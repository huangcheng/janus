**1. Verdict:** GO WITH FIXES — the failure-mode-first design is sound, but gateway TTL freshness, 429 backoff contradictions, and pool-exhaustion edges must be resolved first.

**2. Critical risks**
- Probe cost/rate blowback: DashScope 262×3; probes share live RPM pools; batch cap 1000 / daily 5000 / 786 bootstrap unreconciled.
- Deny-regex false positives mitigated (anchored; input-shape default), but one wrong seeded code row removes a good key for 24h.
- Failover latency: 45s default exceeds 30s client budgets; worst case ~135s inside 300s idle_timeout — documented footgun.
- Retry storms: no pool breaker; deny-shaped 400s multiply upstream calls until the matrix loads.
- Balance starvation: request-time 60s cooldown vs 1h matrix TTL re-tries a dry key ~60×.
- Streaming: 2xx committed at `stream_reply`; 200-with-error-body unaddressed.

**3. Contradictions/stale**
- A.2 429: "halve in-flight 30s" vs "pause that provider's probe 30s".
- A.1: 401/403 "leave prior rows untouched" vs the `__key__` broken row that same flow must write.
- Part B ships an sqlite variant then declares it nonexistent ("illustrative only"; "no sqlite DDL exists").
- Part B "gateway reads are fresh by construction; nothing re-checks checked_at" contradicts ETS persistence between polls — balance can outlive 1h.
- Balance: A.1 1h TTL vs C.1 60s cooldown.
- "One bump_generation per batch" vs codes-table writes bumping generation.
