**1. Verdict:** GO WITH FIXES — unusually disciplined spec (fail-open defaults, TTLs, budgets, one classifier), but the worst-case latency arithmetic, Part E deploy order, and two overlapping fail-open paths must be fixed first.

**2. Critical risks**
- *Probe blowback:* pacing/budgets are solid, but "the provider's known RPM" has no defined source, and single-key probes claim "bounded ~2–4 min" while 262 models × 15s timeout can far exceed it (no wall cap specified for single-key).
- *Deny-regex vs input-shape:* anchored regex scoped to code/message fields is right; residual risk is seed coverage — an unseeded provider classifies every 400 as "unclassified → retry once," silently changing behavior vs seeded ones.
- *Latency vs idle_timeout:* the ceiling formula reserves ONE 30s classification-body cap, but every failed attempt can collect one. With the allowed range `failover_max_attempts ∈ [0,20]`, worst-case wall (budget + TTFB + N×30s bodies) can blow past the 300s idle_timeout. Real hole.
- *Retry storms:* no pool-level breaker; concurrent requests snapshot the pool pre-cooling and each burns the dead key once. 429s lacking Retry-After get only a 10s cooldown → key-cycling under load.
- *Reload races:* per-request generation snapshot correctly kills mid-request mixing; but the catalog poll interval is never stated, so broken-key propagation lag is unquantified.
- *Balance starvation:* well handled (1h TTL, canary-first healing, reserved budget share).
- *Rotation:* clean (delete rows + bump generation); residual exposure = poll lag.
- *Streaming boundary:* sound — error-status bodies are collected pre-commit; 200-then-SSE-error after first frame is non-retryable (implicit, acceptable).

**3. Contradictions / stale claims**
- Deploy order says E.3 ships before E.2, but E.3's `WHERE is_terminal` requires E.2's column — self-contradictory.
- "total ≤ max_attempts + 2 calls" undercounts if both pool_reuse and the provider-retry slot fire (+3).
- A.2 429-rate: "skip this model" vs "pause provider 30s" — pick one.

**4. Missing requirements**
- Generation-poll interval / propagation SLA.
- RPM source for pacing (or drop the clause).
- `probe_budget_counters` schema.
- Cap on the retained request body re-marshalled per attempt.
- Traffic rows stamp the *gateway* event timestamp while arbitration uses the DB clock — no skew bound given.

**5. Architecture notes**
ETS snapshot-at-dispatch is the right concurrency story; billing `WHERE is_terminal` is correct (accept the 300s backfill lag + 1s-buffer loss); the codes-table unifying probe/refresher/retry classification is the strongest element; knob delivery via persistent_term matches repo invariants.

**6. Top 5 edits**
1. Fix ceiling: budget + TTFB + body_cap×(1+attempts) + margin ≤ idle_timeout, or charge body collection to the budget; narrow the attempts range accordingly.
2. Reconcile Part E: one migration owns the new usage columns; fix the ordering text.
3. Merge Part B zero-eligible fail-open with C.1 loop fail-open: one rule, one counter, ≤1 per request.
4. State the poll-interval SLO and the RPM source.
5. Correct the total-attempt bound (pool_reuse + provider slot) and stamp traffic rows with DB time.
