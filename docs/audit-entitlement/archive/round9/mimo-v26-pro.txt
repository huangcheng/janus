**1. Verdict: GO WITH FIXES** — the design is sound and unusually careful, but a few internal contradictions (attempt accounting, TTL enforcement point, error_code deploy order) must be resolved before implementation.

**2. Critical risks**
- **Probe blowback:** probes share live rate pools; only reactive 429 backoff exists. 786-call DashScope bootstrap at 150ms spacing ≈ real RPM consumed; no live-traffic headroom reservation.
- **Deny-regex false positives:** `product.*未开通`-class patterns are OK, but codes-table regexes are validated in Python `re` yet compiled in Erlang `re` — dialect divergence (lookbehind, unicode classes) can silently flip classification; no ReDoS timeout at gateway classify time.
- **Failover latency:** 45s budget + 60s TTFB + 30s body cap + jitter fits the 300s idle_timeout ceiling, but 105s worst-case first-call path holds Cowboy handlers and gun connections across bursts; no pool-level breaker means concurrent failures cascade into held connections.
- **Retry storms:** empty codes table → all 429s rate-class → whole-pool traversal per request; the 10s floor helps but amplification is per-request-unbounded within budget.
- **Rotation staleness:** per-request snapshot can hold a rotated secret up to ~180s after a secret update clears rows and bumps generation.

**3. Contradictions / stale claims**
- A.1 "consumers enforce by `checked_at`" vs Part B "the SQL is the ONLY TTL enforcement point — nothing re-checks gateway-side."
- Attempt accounting: "total ≤ max_attempts + 2" excludes the pool_reuse slot (a further key call), so the real ceiling is max_attempts+3; pseudocode never says pool_reuse increments key_retries.
- Test 16 "the coolest key is reused" vs C.1 "cooldown-EXPIRED, least-recently-used... never the one that just failed" — and undefined when all attempted keys still cool.
- `request_ref` = "one UUID per loop" (C.1 pseudocode) vs "groups the attempts of one client request."
- "the attempt's usage row is classifier feedback" requires `error_code` (E.1), but E.1's deploy position vs Part C is unstated; E.3/E.4-first ordering doesn't cover it.
- 5xx "return the best error" vs exhaustion "error from the highest attempt index" — 'best' undefined.

**4. Missing requirements**
- Rate headroom policy for probes (fraction of provider RPM reserved for live traffic).
- `key_scoped_balance` default per provider and who sets it.
- Regex dialect/validation contract binding Python and Erlang semantics.
- Explicit single combined usage migration (error_code + attempt/request_ref/is_terminal) to avoid two gateway migrations.
- Behavior when the whole pool is cooling mid-loop (before deadline).

**5. Architecture notes**
- One snapshot at `dispatch/7` threaded through attempts correctly solves the reload race; note_failure no-ops on vanished keys — consistent.
- Per-attempt rows with `WHERE is_terminal` billing is clean; legacy backfill stated.
- Write ownership (dashboard-only) and carrier-tolerant reads are right; Postgres-only matrix with defined fail-open is honest.
- 429 dual-class centralized in `entitlement_codes` — good single-sourcing, but the "missing table = rate-class" default maximizes exactly the amplification risk above.
- Knob delivery via persistent_term + write-time validation + apply-time clamp is belt-and-suspenders as claimed.

**6. Top 5 edits**
1. Reconcile attempt math: state total call ceiling including pool_reuse; define reuse when all attempted keys cool.
2. Fix A.1/Part B TTL contradiction: declare SQL the sole enforcement point.
3. Merge E.1 error_code into E.2's migration; fix deploy-order list to precede Part C.
4. Add probe rate headroom (e.g., ≤30% provider RPM, yield to live traffic) beyond reactive backoff.
5. Specify regex cross-dialect validation (Python+Erlang compile check, ReDoS timeout) and define 'best error' = last attempt's error; clarify `request_ref` per client request.
