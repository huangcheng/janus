# Audit: Key Entitlement Matrix + In-Request Key Failover

## 1. Verdict
**GO WITH FIXES** — the design is coherent and failure-mode-aware, but the budget-ceiling arithmetic, the traffic-learning chicken-and-egg on `error_code`, and a few under-specified races need edits before implementation.

## 2. Critical risks
- **Probe cost/blowback**: 1000-call cap per provider × scheduled healing every 15min can re-fire constantly on large catalogs (DashScope 262 × 3 keys = 786 calls/batch). Budget math vs the 15-min loop is never reconciled — with 150ms pacing and 2-key parallelism, a full provider probe approaches the 10-min wall cap and can starve the queue.
- **Deny regex vs input-shape 400s**: fail-open default is right, but `input_shape`-flagged `ok` rows re-probe every 1h — a stable `no permission` model (content policy) burns probe quota forever. Needs a re-probe circuit breaker or escalation.
- **Latency ceiling**: 240s ceiling logic is sound, but per-attempt TTFB timeout is assumed 60s and never stated as a dependency; if operators lower it, the ceiling doesn't adjust.
- **Retry storms**: a provider-wide outage with 3-key pools gives up to 5 calls/request; combined with client retries this is a multiplier. "No pool-level breaker in v1" should be listed as an accepted risk with a metric.
- **Balance-key starvation**: healing loop is the only recovery path; if probe budget is exhausted by deny rows, balance rows wait. Prioritization within the healing queue is unspecified.
- **Reload race**: snapshot-once at `dispatch/7` is correct, but a mid-loop catalog swap can yield a Route whose key was deleted; behavior on deleted-key-id in `note_failure`/cooldown is unspecified.

## 3. Contradictions / stale claims
- A.2 says "Single-flight per provider (in-process lock)" then later says Postgres advisory lock is "the single mechanism; there is no in-process lock" — first sentence is stale.
- C.1 says fail-open triggers when "that empties the pool", while B defines zero-eligible fallback as a *pre-filter* concern; the two fail-open paths (pre-filter vs. retry-loop) should be one.
- A.1: "ok rows valid 7 days" vs re-probe at 3 days — the 7-day validity is dead text since nothing consumes `ok`.

## 4. Missing requirements
- No idempotency-key or request-body mutation rules for retries (safe for chat, but state it).
- No spec for `entitlement_codes` schema columns beyond the classifier signature; carrier SQL for it is absent.
- Probe requests through proxies/TLS-verify settings of the provider config — unspecified whether probe honors provider-level egress config.
- No metric/alert list (only one counter named).
- Key rotation: "queues a re-probe bootstrap" — queue persistence across dashboard restart unspecified.
- Flow 19 (kill gateway mid-retry) is not realistically automatable in the local gate; needs a defined harness.

## 5. Architecture notes
- ETS snapshot-per-request is the right call; confirm the deny map is captured *inside* the same catalog lookup as the key pool, or the two reads can straddle a generation swap.
- `is_terminal` billing: dashboard-side crash-marking after 5min means terminal attribution lags; aggregation queries during the grace window undercount — acceptable but undocumented.
- 429 dual-class split (balance vs rate) depends on `entitlement_codes` coverage; an unclassifiable 429 must default to RATE-class (bench briefly), not balance — the spec never says.
- Gateway read of `entitlement_codes` duplicates the classifier in Erlang; "one table, two implementations" still risks drift — state that Erlang implements table-lookup + regex only, no hardcoded codes.

## 6. Top 5 edits
1. Fix A.2 lock wording to advisory-lock-only; delete the in-process sentence.
2. Merge B's zero-eligible fail-open and C.1's fail-open into one rule, applied once per request, with the counter fired exactly once.
3. Add healing-loop queue priority: secret-rotation > balance (age-ordered) > deny > ok-stale; cap per-tick provider coverage so the 15-min cadence can't fall permanently behind.
4. Specify unclassifiable-429 → RATE-class default, and `error_code` absence in usage events → traffic learning stays ok-only (reaffirm as a hard gate, not a footnote).
5. Delete the "ok valid 7 days" sentence (or state it's documentation-only); add probe egress config inheritance and the `entitlement_codes` carrier SQL.
