**1. Verdict: GO WITH FIXES** — the core design (per-request catalog snapshot, single classifier table, bounded loop) is sound and largely self-consistent, but there are three correctness bugs plus several ambiguous defaults that must be resolved in-spec before implementation.

**2. Critical risks**
- Probe cost: DashScope day-one 786 fits the 5000/provider day + 25% healing reserve, but there is no *global* cap across providers and no mechanism to measure probe share of live RPM; in-flight halving is a weak guard against live 429s.
- Regex false positives: `no permission` → input_shape → `ok` keeps a genuinely unauthorized key eligible forever; every request then pays a bounded failover + terminal error. Acceptable trade-off, but tests 8/F depend on locally seeding the same phrases — state this dependency.
- Failover vs idle_timeout: worst wall (180+60+30+jitter ≈ 270s) fits 300s; the 45s default exceeding 30s clients is acknowledged; non-stream bodies buffered × attempts.
- Retry storm: any *new* provider-wide failure class (401/5xx on all keys) costs one hit per key per in-flight request before cooling bites.
- Reload race: snapshot design is right, but probe rows written mid-batch are invisible to gateways until the batch-end bump (up to 10 min staleness).
- Key rotation is handled (row delete + gen bump); the re-probe window leaves a bad key eligible, healed only by failover.

**3. Contradictions / stale claims**
- Zero-eligible fail-open picks "any non-cooling, non-attempted key" vs "all-broken pool terminates with broken evidence" and "broken keys are skipped from candidates entirely." Broken keys must be excluded from the fail-open pool; no test covers this.
- 429 fail-open: "retryable, no cooldown" vs "codes-table-empty 429s carry a minimum 10s cooldown."
- "One bump_generation per batch" vs A.2's immediate bump on 401 abort.
- "Both writers are dashboard processes, one DB clock arbitrates" — traffic rows carry *gateway* timestamps; unless `usage_events.ts` is DB-side NOW(), the watermark guard is skew-exposed.
- Probe "in-process lock" vs "advisory lock is the single mechanism"; healing-loop cross-replica single-flight unspecified.
- Premarked input_shape rows "never enter the hourly loop" vs "input_shape-flagged ok rows re-probed after 1h."
- Probe unclassified-400 → `ok+input_shape` (terminal) vs retry-time unclassified-400 → one failover: an intentional-looking asymmetry that is nowhere declared.

**4. Missing requirements**
- Canary semantics: only a 200 or 429-rate canary may clear a key's `balance` rows; a canary *deny* must not.
- Cost/spend analytics over non-terminal attempts (failover spend is invisible under is_terminal-only aggregation).
- Enforcement/measurement of "never more than provider's known RPM" for probes.
- E2E flow "all keys broken → terminal with broken evidence."

**5. Architecture notes**
- ETS generation snapshot threaded per request + lock-free reads: correct, and fail-open correctly draws from the same snapshot.
- is_terminal-only billing is defensible but needs a companion spend report over non-terminal rows; keep both.
- 429 dual-meaning centralized in one table is good — just don't ship the empty-table no-cooldown path.
- Accounting (≤ 1 + max_attempts key calls, provider slot reserved) is clearly specified; total ≤ attempts+2 is right.

**6. Top 5 concrete edits**
1. Part B zero-eligible rule: fail-open candidate set **excludes `broken` rows**; all-broken ⇒ terminal error; add flow 20.
2. C.1 429 clause: replace "no cooldown" with "min 10s cooldown, still retry on other keys."
3. A.1: stamp `usage_events.ts` with DB-side NOW() (or document skew window); fix the one-clock claim.
4. A.2: "bump once per batch; immediate bump *only* on key-broken abort"; delete the in-process lock sentence.
5. A.4: canary clears balance rows only on balance-resolved evidence (200 / rate-class 429); deny canary ⇒ per-row re-probe.
