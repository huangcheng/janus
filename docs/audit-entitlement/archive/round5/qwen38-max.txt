**1. Verdict**
GO WITH FIXES — sound fail-open posture and good race handling, but budget semantics, balance healing cost, and usage-row lifecycle need fixes before implementation.

**2. Critical risks**
- **Probe cost/rate-limit blowback**: DashScope = 262 models × 3 keys ≈ 786 paid calls/probe cycle; healing re-probes every 15 min can eat the daily budget during a provider-wide incident. Probes share rate pools with traffic.
- **Balance starvation via volume**: `balance` is stored per (key, model) but is key-level state. Healing re-probes *every* balance row (262×N per key) — budget exhaustion guaranteed under a provider-wide 429. Needs one canary probe per key generalizing to all its rows.
- **Retry storms**: cooling is set only after a failed response returns, so a burst of N concurrent requests all hit a dead key before cooling engages (bounded by concurrency × attempts, but real). No pool-level breaker in v1 — acknowledged, accept explicitly.
- **Deny-regex false positives**: well mitigated (code/message fields only, narrow wording, fail-open default), but gateway-side behavior when `entitlement_codes` is **missing/empty** is unspecified — gateway can boot pre-seed.
- **Failover latency**: math checks out (210s ceiling vs 300s idle_timeout); client-side 30–60s abandonment is the real risk, acknowledged.
- **Streaming boundary**: error-status streams correctly stay retryable; 2xx committed at `stream_reply`. Gap: some providers emit 200 + error JSON in the first SSE frame — terminal-as-success hides it.
- **Rotation staleness**: re-probe queue is in-memory; dashboard restart after secret rotation leaves the key row-less with no trigger to re-probe it (healing only scans existing rows). Must persist the queue or have healing adopt row-less keys.

**3. Contradictions / stale claims**
- A.2 "batch ABORTS at JANUS_PROBE_MAX_CALLS" vs A.4 "per-provider DAILY budget shared across all three triggers" — same knob, two semantics.
- A.2 "single-flight per provider (in-process lock)" vs later "Advisory lock is the single mechanism."
- Healing loop is "ONE global queue" but no cross-replica lock is specified for it (advisory lock only specced for probe endpoints).

**4. Missing requirements**
- Missing-table tolerance for `entitlement_codes` gateway-side (only `key_entitlements` gets it).
- Body-size cap for non-stream collect-then-classify (unbounded buffering today; collect_drain caps only cover streams).
- Usage-row write timing for streaming attempts; crash during a long stream loses the whole row, contradicting "losses bounded by the 1s buffer."
- Dashboard backfilling `is_terminal` writes into gateway-owned `usage_events` — reverse ownership direction; call it out.

**5. Architecture notes**
- Dispatch-entry snapshot of the deny map is the right race fix; binary-key matching correctly mandated.
- Per-attempt usage rows + `WHERE is_terminal` billing is clean; ensure terminal row always flushes in the same batch window.
- Provider-wide rate limits: rate-class 429 deliberately skips cooldown; the provider-retry slot reusing the "coolest" key can immediately re-hit a still-throttled key.
- Knobs via persistent_term match repo invariants; also clamp at gateway read, not only settings-write.

**6. Top 5 edits**
1. Split/unify the probe budget: per-batch cap vs daily budget — two knobs or one definition.
2. Make `balance` healing key-scoped: one canary probe per key updates all its balance rows.
3. Resolve the single-flight contradiction; require advisory locks for healing + bootstrap across replicas.
4. Add `entitlement_codes` missing-table fallback (empty → rate-class, no deny) + non-stream collect size cap.
5. Specify streaming usage-row write timing, extend the accepted-loss note, and persist the rotation re-probe queue (or make healing adopt row-less keys).
