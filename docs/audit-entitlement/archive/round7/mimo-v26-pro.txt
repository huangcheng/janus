**1. Verdict: GO WITH FIXES** — fail-open design is sound, but a C.1↔D contradiction on 400-retry, an undefined provider-retry pick, and no broken-key healing must be fixed before coding.

**2. Critical risks**
- **Probe blowback:** 150ms spacing × 2 keys ≈ 13 rps/provider, sharing live rate pools (spec admits). A 262-model DashScope bootstrap can bench healthy traffic keys; only mitigation is 30s halve-backoff. Cap probe concurrency 1 + per-provider RPS.
- **Deny false-positives:** `not activated` can appear in echoed prompt text *inside* message fields; restrict regex to provider `code`/structured message only — a false deny removes a good key 24h (the worse failure per spec's own logic).
- **Latency:** ceiling arithmetic omits jitter and assumes the 30s body-cap applies once; per-attempt TTFB+cap can stack before the deadline gates. Lower default for 30s clients (spec concedes) or compute worst case honestly.
- **Retry storms:** N concurrent clients × 3-key failover on provider outage = ×4 attempts; only per-key cooling damps. Acceptable but needs counter alerting.
- **Reload races:** entry-snapshot threading is right; verify the fail-open pick and usage `request_ref` grouping survive reloads (both asserted, unproven).
- **Starvation:** v1 forbids traffic demotion (no `error_code`), so a key that goes broke mid-day gets only 60s cooldowns — never a matrix `balance` row until the 15-min canary. Confirm acceptable.
- **Rotation:** secret swap → rows cleared → key is unknown=eligible immediately; a bad secret eats failover attempts until bootstrap probes land.
- **Streaming:** spec assumes error-status streams never reach `stream_reply` (collect_drain). If any code path forwards status early, deny-400 retry silently dies. Verify against current handlers.

**3. Contradictions / stale claims**
- C.1: unclassifiable 400 → ONE failover; flow 8: input-shape 400 → NO retry. Direct conflict.
- C.1 "cooldown-expired LRU" vs flow 16 "coolest key"; undefined when all attempted keys still cool down.
- 429 balance: 60s cooldown at retry vs 1h matrix TTL — inconsistent policy for one state.
- "embeddings…when they exist" — they likely exist today; stale claim, scope creep risk.
- A.1 "traffic re-admits escalated rows in v1" vs A.3 promote-only; clarify that promotion is the sole traffic write.

**4. Missing requirements**

- `entitlement_codes` maintenance: who adds rows for new deny wordings, at what cadence (E.1 feedback owner).
- Advisory lock: does probe share the model-sync lock key (serialization intended?) and is it released on abort?
- Crash-marking "usage refresher" isn't in E-list; who runs the 300s grace scan?
